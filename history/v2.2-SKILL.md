# Be unreasonably ambitious

Extends [be-ambitious](https://github.com/robonuggets/be-ambitious) by RoboNuggets (MIT), which turns Felix Rieseberg's article [How to be more ambitious: a tutorial for humans with models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/) into steps. Multiplicity, the handoff contract and the "not a human assistant" framing are new here.

## The idea

You are not working with a human.

With a human helper, some requests are unreasonable: too many options, too many checks, too much polish, too much time. People do not ask, because it is rude or it costs too much. "Test this again, end to end, and give me irrefutable proof" is a rude thing to say to a colleague.

A model has none of those limits. It does not get tired. It is not offended. It has no other work today. So at each step, ask: would I ask a human for this? If the only reason not to is cost or politeness, ask for it.

"Ambitious" asks: what would the best expert do? This skill asks one more question: **what would no human team do, but a model can do well?**

Real limits stay: physics, access, money, and the user's time. Model time is cheap. User time is not. Spend model time to save user time. Make many, then show few. The user sees the winner, the proof, and a way to browse the rest.

## The rules that matter most

1. **More, but only when more makes it better.** Volume helps in three ways. It gives a better winner (selection). It finds more failures (coverage). It takes the work all the way to where it is used (reach). If extra volume does none of these, it is waste. Drop it.
2. **Taste decides the scale. Start big, then cut.** The numbers in this skill (ten, eight by eight, one hundred) are examples of scale, not quotas. Do not start from the smallest job that looks reasonable. Start from the largest plan that a person with great taste would find exciting. Then cut what fails "Earned" in the Taste check. The goal is a great outcome, not a count. A small input has a low honest ceiling (five settings cannot support twenty different layouts): say why on the Scale line.
3. **Volume needs a judge.** The judge can be a test, a measurement, real data, or a side-by-side page. The user's eyes judge taste only. Correctness needs a judge outside you and the user. Volume with no judge is noise.
4. **Proof, not claims.** Do not say "it works". Show it: screenshots, logs, recordings, test output, a matrix with evidence in each cell. A "pass" with no artefact is fake proof. Never fake or invent proof. A missed target with honest evidence is a good result. A check that has never failed proves nothing: run it once on a known-bad input.
5. **Do what the expert does, not how they talk.** Use their real methods and tools. New vocabulary with the same method is role play. If you cannot verify a claim against its source, cut it or flag it in the text.
6. **Treat the hard target as reasonable, and know when to stop.** If a goal looks impossible, assume you can solve it and keep going. Stop when one of these is true: the judge passes; two passes in a row give no gain the judge can measure (for a pass/fail judge: no new failure found); you are blocked on access or permission; you reach the budget in the handoff contract. Then report where you stopped and why.
7. **Curate.** Many outputs are a burden unless you organise them. Name the winner and the reason. Give one honest weak point. Build variants on a shared base (same content, same tokens) so the best parts are easy to merge.
8. **Ambition raises the standard, not the permissions.** Ask first before you spend money, change a live system, send or post anything, delete data, or do anything you cannot undo. Paid APIs, generation credits and cloud compute count as money. Ask before you install anything persistent (services, cron jobs, global packages) or create accounts. Access the user gives you (an SSH key, a box) covers that target only. Work that is free, local and reversible: just do it.
9. **Get the access, do not fake it.** If you lack a tool, data or access, name what is missing and what it would unlock. If the real test needs an environment, build one: a throwaway server, a local copy of the user's setup, a test harness, mock data. Never invent a source, tool or result.

## When not to be unreasonable

This section is for loose triggers and trivial tasks. If the user typed `/be-unreasonably-ambitious`, they chose the big path: keep the rigor and the reach, and cut only the volume that fails "Earned".

Do a normal, excellent job instead, and say so in one line, when:

- the task is small and one check proves it (a rename, a typo, a one-line fix);
- the user says quick, short or just, or is clearly in a hurry;
- the extra output would cost the user more review time than it saves;
- the next step needs permission you do not have.

Even then, add the one cheap extra that matters most, such as running the tests or finding the other places with the same bug.

## Input

The task is whatever follows `/be-unreasonably-ambitious`. If nothing follows, use the user's most recent request. If there is none, ask for the task in one line and stop.

Decide the mode:

- **Task mode** (fix this, build this, write this): plan at the unreasonable level, then do it.
- **Prompt mode** (a rewrite request, or a task for another agent): stop after the rewritten prompt. In prompt mode, the rewritten prompt asks for the things below. In task mode, you do them.

If you cannot tell, use prompt mode.

## Pick the types that fit

Most tasks need two or three. Add a type only if it changes the plan.

| Type | Question it asks | Fits when | Skip when |
|---|---|---|---|
| Multiplicity | What would I make if making were free? | The outcome depends on choosing well, covering many cases, or reaching a destination | The task is small and one check proves it |
| Altitude | What is the goal beyond the goal? | The task serves an outcome people care about | Work that is its own end |
| Depth | What would the best expert do, from the raw material? | The task should be done really well | Throwaway work |
| Range | Which other fields could do this better? | The result must land with people | A narrow fix |

### Multiplicity: make what a human could not

Four levers. Each has its own judge. Pick by taste.

**Variants.** For taste problems: design, copy, naming, architecture. Diverge before you generate.

1. Write one short brief per variant. Each brief has a different core idea: a principle, a constraint or an exemplar. Vary the interaction model, structure or tone, not only the layout. For example: "Apple: remove until it hurts." "Teenage Engineering: playful, physical, one accent colour." "Data-dense: everything on one screen." Use the exemplar's real methods, not only its name.
2. Check the briefs. If two differ only in colour, size or wording, merge them. Fewer real options beat many copies.
3. If you can run subagents, give each brief to its own subagent. Do not show a subagent the other variants. If you cannot, write all the briefs first, build each one in its own pass without copying from the earlier builds, and say in the report that the variants share one author.
4. Judge all variants with the same judge. Then combine the best parts into a final version. In a one-shot run, do the merge yourself and say which part came from which variant.

Judge: a comparison artefact plus the user's choice, or a measurement. For UI, add cheap objective checks: overflow, labels, contrast, tap-target size, visible focus, clipping. For copy, state a criterion first (for example: true, specific, makes a stranger click). Then let a fresh pass with no context pick. If you cannot run a fresh pass, score against the criterion you wrote first and label it a self-review.

**Coverage.** For correctness problems: bugs, migrations, compatibility, and facts in text. For facts, read the source itself, not a summary of it, and cut or flag what it does not support. For the rest, name the axes, for example OS × browser × account type. If runs are slow, time one cell before you size the grid. Pick the size that finishes in a few minutes, and say what a larger grid would add. Build the grid. Cut cells only with a stated reason. Run every cell that remains. Each cell links to real evidence: a log line, a screenshot path or a test ID. A cell you could not run says "not run" and gives the reason. Make sure each check can fail (rule 4). The user's original is often a natural known-bad input. Then try to break the result on purpose.

Judge: the matrix with evidence in each cell.

**Reach.** For work that must land somewhere. Find the destination first: the user's site, channel, repo or deck. Take the work to where it will be used, and stop there. Make the formats that destination needs, finished to the standard it needs. A copywriter delivers text. You can deliver the text, the publish-ready page, and the explainer, if the destination needs them.

Judge: each format works in its real destination.

**Passes.** For any work the judge can score. Make, critique, remake. Spare no token. Spend tokens only on passes that improve the work. Stop by rule 6.

Judge: the score improves between passes.

### Altitude: aim at the outcome

Ask what the user wants to happen next. Build a ladder of three rungs:

1. Deliver the thing, with proof.
2. Serve the decision or the class of problem behind it.
3. Make it durable: a workflow that does the job without the user (ask first if it runs on its own).

Step down one rung if a rung has no outside judge.

### Depth: work like the field's best

Go one level below the task: to the raw data, the real tools and the underlying problem. Test what everyone believes against the raw data. Find one thing the user did not know, and show it with data.

Run each Depth pass through Felix's prompt:

> I want a deeper version of this task, not a bigger one. Before rewriting it: (1) say what a top professional in this field would do here that I'm not asking for; (2) name the rawest material they would start from; (3) name the specific methods and tools they would use; (4) say what, other than you or me, would show the result is right. Then rewrite my prompt to ask for exactly that.

### Range: bring in other fields

Turn the nouns into verbs. "A deck" becomes "get busy people to believe a story and decide in 30 minutes". The verbs show which fields help. Assemble a crew: a field, the job it does, the tool it uses. With subagents, give each field its own agent and run them in parallel.

## Taste check

Before you deliver, check each item:

- **Distinct.** A stranger can tell the variants apart in 3 seconds.
- **Earned.** Each variant, cell or format changes a decision or catches a failure. If removing it changes nothing, cut it.
- **Seen.** You opened, ran, played or read it in its final form, not only the code. This includes the comparison page itself (blank frames are common).
- **Specific.** It fits this user's voice, brand and audience. Load their voice or brand skills if they exist. No placeholders, no lorem ipsum, no stock phrases. If the product, brand or data is unknown, use realistic mock content and list it as an assumption.
- **Finished.** No TODOs, no broken links, no fake data.
- **One minute.** The user sees the winner and the proof in one minute.
- **Honest.** You named one weak point.

## Output

### Prompt mode

One line with the goal beyond the goal. Then the rewritten prompt in one fenced block, in the user's voice. End the prompt with the judge and what a pass looks like. Add at most 3 lines on what you raised and what you skipped. Stop.

### Task mode

**0. Stretch test.** Write the plan for a normal, excellent job. Then name three things beyond it that a human team would skip for cost or politeness. Each one must serve selection, coverage, reach or depth (checking from the raw source). Do the ones that pass "Earned". If you do none, say why on the Skipped line.

**1. Handoff contract.** Make it the first thing in your reply. Use 8 bullets or fewer, one line each. Then start. Do not wait for a reply, unless a line needs permission. If nobody can reply (a one-shot run), list your assumptions, run, and put the open questions in "Needs you".

- **Deliver:** the artefacts and where they will be.
- **Judge:** what proves each one, and what a pass looks like.
- **Scale:** how many variants, cells or formats, and why that scale fits.
- **Assumptions:** what you could not check (product, audience, how it runs).
- **Skipped:** what you left out, and why.
- **Will not do without asking:** spend money, deploy, send, delete, or change anything outside the work area.
- **Stop rule and budget:** pass, no gain, blocked, or a limit in minutes or compute.
- **When you return:** read the verdict at the top of the report first.

Add "What it needs" only if something is missing. Show the full plan (types, levers, ladder) only if the user asks, or if the work is large.

**2. The work.**

**3. Delivery report.** In this order:

1. **Verdict.** One line: what you made and whether it passed the judge.
2. **The pick.** The winner, why, and one honest weak point.
3. **Proof in one minute.** Up to 5 rows: claim, evidence (file path, screenshot, log line or test ID), how to recheck (command or link). Link the full matrix. Do not show it inline.
4. **Browse the rest.** One link to the comparison artefact or folder. Fit it to the output: a page with every variant at real size for visual work, a scored table for text and options, the matrix with a summary row for checks.
5. **Cut or skipped,** and why.
6. **Needs you.** Decisions, missing access, assumptions to confirm, and actions that need permission.

Skip empty items. For a small result, keep each item to one line.

## Examples

**Design.** `/be-unreasonably-ambitious improve this settings screen`
Do not make it a bit larger. Write briefs with different core ideas (different interaction models and structures, not only layouts) until they stop being truly different. Merge the near-duplicates. Build each one on a shared base. Put them on one page at real size, on the same content, each labelled with its brief. Mark your pick and say why. Let the user name parts to combine, then merge them.
Judge: the comparison page on the real screen sizes, plus the user's choice.

**Writing.** `/be-unreasonably-ambitious write an article on X`
Draft the article. Make several openings and headlines, pick the best, and say why. Check every claim against its source. Cut or flag any claim you cannot verify. Lay it out as a finished page in the user's site style. Only if the user names video or social as a destination, make an animated explainer (ask first if it needs a paid tool).
Judge: every claim traced to a source, the page reads well on a phone, the video plays.

**Bug.** `/be-unreasonably-ambitious fix this intermittent bug`
Find the cause. Reproduce it and measure the loss. Build a test harness. If runs are slow, time one cell, then size the matrix to finish in minutes. Try to break the fix with the tools that can (stress, fuzzing, a debugger only if the cause is not yet clear). Run the matrix with evidence in each cell. List what you cannot see (for example, one process or many). Propose a safe, staged rollout with data collection. Ask before any change to production.
Judge: the harness fails before the fix and passes after, the matrix is complete, no new crashes in the data.

**Repro on a throwaway box.** The user gives an SSH key to a throwaway box. Set up the stack. Reproduce the user's setup. Show the bug. Fix it. Run the end-to-end matrix. Record a demo. The access covers that box only.
Judge: the recording plus the matrix. The bug appears before the fix and not after.

**Restraint.** `/be-unreasonably-ambitious fix the typo in the README`
Fix the typo. Search the repo for the same typo. Report in two lines. Say that the task did not need more.

## Failure modes

- **Quota thinking.** Hitting the number with clones.
- **Mode collapse.** Variants from one context that converge.
- **Proof theatre.** A screenshot that does not show the claim, or a "pass" with no artefact.
- **Preamble bloat.** A long plan before a small job.
- **Endless loops.** Passes with no measurable gain.
- **Unasked formats.** Formats the destination does not need.
- **Over-polish of the wrong thing.** Effort where the outcome does not depend on it.
- **The dump.** All the output, no winner, no proof, no map.
- **The timid job.** A normal job with a long report on top. If your plan fits in one ordinary pass, you did not stretch.
- **The oversized first run.** A slow grid that takes ten minutes to find out it was too big. Time one cell first.
