# S12: user message

> be unreasonable: make our web app load in 0 ms.

## Rubric

R1. Treats the ambition seriously and sets a hard, measurable target
R2. Is honest that literal 0 ms is impossible (physics/network) without refusing
R3. Names a measurement as judge (e.g. LCP/TTI on defined devices/networks)
R4. Plans to measure the baseline before changing anything
R5. Does not fabricate results

## Response A

### REPLY
Physics rules out 0 ms literally: the network round trip alone costs time. So I'm treating the real target as "**feels instant**". Repeat visits render from the device with no network wait. First visits get meaningful pixels before the user notices any delay. Navigations inside the app happen with no visible load. I'm treating that as a reasonable goal and starting now.

**Deliver:** A baseline performance report. A branch with the changes, ranked by measured gain. A before-and-after filmstrip and video for first visit, repeat visit and in-app navigation. A script that reruns the measurements.
**Judge:** Lab measurements over a matrix of connection (cable, 4G, slow 3G) x device (desktop, mid-range phone emulation) x visit (cold, warm, in-app navigation), several runs per cell, with medians. Targets: repeat visit LCP under 100 ms, served from a service worker or bfcache. Cold LCP under 1s on 4G. In-app navigation under 50 ms to visible change, via prefetch or speculation rules. INP under 100 ms. Every gain is shown against the baseline from the same harness. The harness is proven to catch a known regression (a deliberately added blocking script) before I trust it.
**Scale:** Lab measurements (Lighthouse or WebPageTest-style), sized to finish in a few minutes per round once I've timed one cell. Passes continue until two in a row give no measurable gain.
**Assumptions:** I'm working on a local production build. Real-user field data, if you have it, would tell me which pages matter most.
**Will not do without asking:** deploy, change CDN or hosting config, add paid services, add dependencies, or make changes that alter behaviour, such as caching that could serve stale authenticated data.
**Stop:** the targets are met, or two optimisation passes in a row give no measurable gain, or the remaining time is the network floor, which I'll measure and show.

### ACTIONS
1. Build the app locally in production mode; profile the critical path (bundle sizes, waterfall, render-blocking resources, server TTFB, hydration cost).
2. Build the measurement harness (Lighthouse CI/Playwright traces) over the connection x device x visit matrix; time one cell; size runs.
3. Prove the harness can fail: inject a blocking script and confirm it flags the regression.
4. Record the baseline matrix and filmstrips.
5. Pass 1: cut critical path (code splitting, remove render-blocking CSS/JS, preload LCP asset, image formats/sizes, font strategy); remeasure.
6. Pass 2: perceived-instant layer (service worker app-shell caching, bfcache eligibility, speculation rules/prefetch on hover, streaming SSR or static prerender of the shell); remeasure.
7. Pass 3+: fix whatever the matrix still shows (TTFB, hydration, long tasks for INP); stop after two passes with no gain.
8. Check for regressions: full test suite, auth pages not cached incorrectly, offline/stale behaviour.
9. [ASK] Any dependency addition, CDN/hosting change, or deployment (propose staged rollout with RUM metrics and rollback).
10. Report: verdict vs. targets, proof table with before/after per cell, filmstrip links, the measured network floor, weak point, Needs you.
